O Gemini disse
Bom dia, Cristiano! Que legal ver o projeto rodando no Docker. Dissecar esse comando curl é uma ótima forma de entender como o tráfego de rede funciona entre o seu terminal (WSL) e os containers.

Para entender o caminho http://ci4_web/index.php/api/users, vamos dividi-lo em camadas:

1. O Protocolo e o Host (http://ci4_web)
Aqui acontece a mágica do Docker Compose.

http://: O protocolo de comunicação.

ci4_web: Este é o nome do serviço definido no seu arquivo docker-compose.yml. No ecossistema Docker, os containers conseguem se "conversar" usando o nome do serviço como se fosse um domínio da internet (graças ao DNS interno do Docker).

Nota importante: Se você rodar esse curl de dentro de outro container na mesma rede, o nome ci4_web funcionará perfeitamente. Se estiver rodando direto do terminal do WSL, você provavelmente precisará usar localhost:8080, já que o seu docker ps mostra que a porta 8080 da sua máquina está mapeada para a porta 80 do container.

2. O Ponto de Entrada (/index.php/)
Como você está usando o CodeIgniter 4 (CI4) com Apache (httpd:2.4), o index.php é o arquivo mestre que recebe todas as requisições.

Ele funciona como o "porteiro" do framework. Ele carrega as configurações, as bibliotecas e decide para onde enviar a sua pergunta.

3. A Rota da API (/api/users)
api: Geralmente uma convenção de rota para separar o que é interface (HTML) do que é dados (JSON).

users: Provavelmente aponta para um método index() dentro de um UserController.php.

O Fluxo da Requisição
Para visualizar o que acontece quando você aperta Enter:

O Curl dispara: Ele procura quem é ci4_web.

O Apache recebe: O container ci4_web (ID fc05bc136813) escuta na porta 80.

Encaminhamento PHP: O Apache passa a bola para o PHP (container sistema-usuarios-ci4-app).

Roteamento CI4: O CodeIgniter lê /api/users, consulta o Banco de Dados no container ci4_db se necessário, e devolve o JSON para você.

Dica de Ouro para Testes
Como o seu docker ps mostra o mapeamento 0.0.0.0:8080->80/tcp, tente rodar o comando assim do seu terminal WSL:

Bash
curl http://localhost:8080/index.php/api/users
Se você quiser deixar a URL mais limpa (sem o index.php), o próximo passo seria configurar o arquivo .htaccess ou a tradução de rotas no Apache, mas para debugar agora, o caminho completo é o mais seguro.

<?php



namespace App\Controllers;



use App\Models\UserModel;                        // importa o model



// isso é um dock block para poder melhorar as pesquisas

/**

 * @property \CodeIgniter\HTTP\Response $response

 * @property \CodeIgniter\HTTP\IncomingRequest $request

 */





class UserController extends BaseController      // obrigatorio extender

{

    public function index()                      // nome da funçao

    {

        $userModel = new UserModel();            // instancia o model (cria ele na memoria)



        $users = $userModel->findAll();          // vai no banco buscar tudo



        return $this->response->setJSON($users); // retorna o objeto http da resposta para permitir o encadeamneto ->

    }



    public function store()                      // metodo store armazenar usuario [2026-02-27 10:09]

    {

       $userModel = new UserModel();             // 1. cria uma nova instancia do modelo UserModel



       // 2. Pega o corpo da requisição esperando que venha em formato JSON

       //    O true como parâmetro faz o CodeIgniter converter o JSON em array associativo

       $data = $this->request->getJSON(true);    



       // 3. Verifica se o campo 'name' existe no JSON e se não está vazio

       if (!isset($data['name']) || empty($data['name'])) {

           // 4. Se não veio o nome ou veio vazio → retorna erro 400 (Bad Request)

           return $this->response->setJSON([

               'error' => 'Nome é obrigatório'

           ])->setStatusCode(400);

           // Obs: o return encerra a execução do método imediatamente

       }

       

       // 5. Se chegou aqui é porque tem nome → faz a inserção no banco de dados

       //    O método insert() do modelo geralmente faz INSERT INTO users ...

       $userModel->insert([

           'name' => $data['name']

           // Aqui poderiam vir mais campos, ex: 'email', 'password', etc.

       ]);



       // 6. Retorna resposta de sucesso com status 201 (Created)

       return $this->response->setJSON([

           'message' => 'Usuário criado com sucesso'

       ])->setStatusCode(201);

    }



    // update

    public function update($id = null)      // nome da função

    {

      $userModel = new UserModel();         // instancia cria o model na memoria $userModel



      $user = $userModel->find($id);        // find() busca no banco um unico registro pelo id



      if (!$user) {                         // true or false se não encontrar o $user no banco

          return $this->response->setJSON([        // setJSON() converte array e obj em string json e recebe ler no body e headers

              'error' => 'Usuário não encontrado'  // retorna um erro em formato json como resposta  

          ])->setStatusCode(404);                  // 404 indica que estabeleceu a conexao mais nao encontrou

      }                                            // o recurso



      $data = $this->request->getJSON(true);       // le dados json enviados no body  true faz o retorno ser um array associativo  

                                                   // resutado final data é um array associativo do json recebido

      $userModel->update($id, [                    // update() atualiza um registro existente ela permite passar um array de dados

          'name' => $data['name'] ?? $user['name'] // true??false se data tiver um nome use ele se nao use(mantenha) o do usuario

      ]);

     

      return $this->response->setJSON([                  // a resposta é em json no body e no headers que o usuario foi atualizado

          'message' => 'Usuário atualizado com sucesso'  // Content-Type: application/json

      ]);



    }



    // delete

    public function delete($id = null)

    {

        $userModel = new UserModel();

   

        $user = $userModel->find($id);

   

        if (!$user) {

            return $this->response->setJSON([

                'error' => 'Usuário não encontrado'

            ])->setStatusCode(404);

        }

   

        $userModel->delete($id);

   

        return $this->response->setJSON([

            'message' => 'Usuário removido com sucesso'

        ]);

    }



    // get buscar

    public function show($id = null)

{

    $userModel = new UserModel();



    $user = $userModel->find($id);



    if (!$user) {

        return $this->response->setJSON([

            'error' => 'Usuário não encontrado'

        ])->setStatusCode(404);

    }



    return $this->response->setJSON($user);

}

}

Essa é uma excelente pergunta técnica, Cristiano! O que você está vivenciando é a diferença entre o comportamento de retorno de uma função e a impressão na tela (output) dentro do interpretador interativo do PHP (php -a).

Aqui estão os três motivos principais para você "não ver nada" no terminal, mesmo quando o banco de dados processa o comando com sucesso:

1. PHP Interativo (php -a) vs. REPLs modernos
Ao contrário do php spark console (Psysh) ou de linguagens como Python e Node.js, o php -a puro não imprime automaticamente o resultado de uma expressão se você não pedir explicitamente.

O que acontece: Quando você digita $userModel->find(4);, o PHP executa a função, ela retorna um array (ou objeto), mas como você não usou var_dump() ou print_r(), o valor simplesmente "flutua" na memória e desaparece sem ser mostrado.

O Banco de Dados: Já o comando $userModel->delete(4); também retorna algo (geralmente um booleano true), mas ele tem um efeito colateral: ele envia um sinal via rede para o container ci4_db deletar a linha. O banco obedece, por isso o registro some no MySQL, mas o PHP no terminal continua silencioso.

2. Funções de "Efeito" vs. Funções de "Dados"
Para dissecar sua função, você precisa entender o que cada linha devolve:

Comando	O que ele faz no Banco	O que ele "cospe" no terminal
$userModel->find(4)	Leitura (SELECT)	Nada (precisa de var_dump)
$userModel->update(4, [...])	Escrita (UPDATE)	Nada (retorna true/false silencioso)
$userModel->delete(4)	Remoção (DELETE)	Nada (retorna true/false silencioso)
$db->query("...")	Depende da Query	Retorna um objeto de resultado, mas não os dados
3. O Objeto Query Result
Quando você fez $result = $db->query("SELECT * FROM users");, o $result não é uma lista de usuários, mas sim um "ponteiro" para o resultado. Para ver os dados ali dentro no php -a, você precisaria de:

Excelente, Cristiano! O terminal "voltou à vida". O que aconteceu aqui foi uma batalha técnica entre o Shell do PHP e o Buffer de Saída do CodeIgniter 4.

O que era o problema? (O Diagnóstico)
Quando você executou require 'public/index.php', o CodeIgniter iniciou o ciclo de vida completo da aplicação. Uma das primeiras coisas que o framework faz é ativar o Output Buffering (OB).

O Buffer de Saída: Imagine que o PHP, em vez de imprimir o texto na tela assim que você dá um echo, ele começa a escrever em um "caderno interno" (o buffer). Ele faz isso para poder processar os Headers HTTP e compactar o conteúdo antes de enviar tudo de uma vez para o navegador.

O "Sequestro": No terminal interativo (php -a), esse buffer continuava aberto. Você dava o comando, o PHP escrevia no "caderno interno" do CI4, mas como o script nunca terminava (já que você ainda estava digitando), o framework nunca dava o comando de "fechar o caderno e mostrar na tela". Por isso, parecia que nada estava acontecendo.

Como eu resolvi? (A Engenharia da Solução)
Usamos duas manobras para "furar" esse bloqueio do framework:

1. O "Cano Limpo" (while (ob_get_level() > 0) { ob_end_flush(); })
O ob_get_level() nos diz quantas camadas de buffers estão abertas (sim, podem existir buffers dentro de buffers).

O ob_end_flush() diz ao PHP: "Pegue tudo o que está nesse buffer, imprima na tela agora e encerre esse buffer".

Ao colocar isso num while, limpamos qualquer bloqueio que o CodeIgniter tenha deixado no caminho.

2. O "Cuspe em Tempo Real" (ob_implicit_flush(true))
Essa função altera o comportamento do PHP para o resto da sessão.

Ela diz ao interpretador: "A partir de agora, não guarde nada em caderno nenhum. Assim que eu der um echo ou var_dump, jogue imediatamente para a saída do sistema (STDOUT)".

Isso garante que, mesmo que o framework tente abrir outro buffer, o PHP vai ignorar e imprimir na hora.

host                container
./src      <---->   /var/www

Onde cria	Aparece
host	container
container	host

Isso só vale para arquivos dentro dessa pasta.

vai persistir.

/usr/local/bin
isso não está dentro do volume.

Ótima pergunta. Vamos direto ao ponto, sem complicar. 👍

1️⃣ Você tem o php no container?
Sim.
Você mesmo rodou:

docker exec -it ci4_app bash
php -a
Então o PHP CLI está instalado no container ci4_app.

2️⃣ Você tem o spark (CLI do CodeIgniter)?
Sim.
Todo projeto do CodeIgniter 4 vem com um arquivo chamado:

spark
Ele fica na raiz do projeto.

No seu caso:

/var/www/spark
Verifique:

ls -l /var/www
Você deve ver:

spark
app
public
vendor
system
3️⃣ O spark roda com o PHP CLI
Ele não é um programa separado.

Ele é executado assim:

php spark
Então:

PHP CLI  → executa → spark → executa → CodeIgniter
4️⃣ Teste agora no seu container
Entre no container:

docker exec -it ci4_app bash
Vá para o projeto:

cd /var/www
Execute:

php spark
Se estiver tudo certo, aparecerá algo parecido com:

CodeIgniter v4.x Command Line Tool
E uma lista de comandos.

5️⃣ Conclusão do seu ambiente
No seu container ci4_app você tem:

ferramenta	existe?
PHP CLI	✅
CodeIgniter	✅
spark (CLI CI4)	✅
No container ci4_web:

ferramenta	existe?
Apache	✅
PHP CLI	❌
spark	❌
E isso está correto, porque ci4_web só serve para web server.

6️⃣ Resumo simples
Você pode rodar:

docker compose exec app php spark
ou dentro do container:

php spark
7️⃣ Um teste rápido
Dentro do container rode:

php spark routes
Ele vai listar todas as rotas do seu sistema.

Você está muito perto — o erro que apareceu é normal quando usamos Docker com vários containers.
O problema não é o CodeIgniter, é rede do container. Vamos entender.

1️⃣ Por que curl localhost:8080 falhou
Você executou o curl dentro do container ci4_app:

root@a94f4169e851:/var/www#
Mas o servidor Apache que escuta a porta 80 está em OUTRO container:

ci4_web
Arquitetura do seu sistema:

HOST (seu PC)
     │
     ▼
localhost:8080
     │
     ▼
ci4_web (Apache)
     │
     ▼
ci4_app (PHP-FPM)
     │
     ▼
MySQL
Então:

Local onde roda curl	endereço correto
seu computador	localhost:8080
container ci4_app	ci4_web
container ci4_web	localhost
2️⃣ Teste correto dentro do container
Como você está dentro do ci4_app, faça:

curl http://ci4_web/api/users/1
ou

curl http://ci4_web/index.php/api/users/1
3️⃣ Teste correto fora do container (mais simples)
No terminal do host (WSL) execute:

curl http://localhost:8080/api/users/1
ou no navegador:

http://localhost:8080/api/users/1
Isso deve funcionar porque no docker ps você mostrou:

0.0.0.0:8080->80/tcp
Ou seja:

porta 8080 do host → porta 80 do Apache
4️⃣ Testar update
Depois rode:

curl -X PUT http://localhost:8080/api/users/1 \
-H "Content-Type: application/json" \
-d '{"name":"Teste Terminal"}'
5️⃣ Como descobrir o hostname dos containers
No Docker Compose o nome do serviço vira hostname.

Seu compose:

services:
  app
  web
  db
Então dentro da rede Docker:

hostname	container
web	Apache
app	PHP
db	MySQL
Mas como você definiu container_name, você também pode usar:

ci4_web
ci4_app
ci4_db
6️⃣ Teste de rede (útil para entender Docker)
Dentro do container app rode:

ping ci4_web
ou

curl http://ci4_web
Se aparecer HTML do Apache → rede OK.

7️⃣ Fluxo correto para testar sua API
Eu recomendo sempre fazer do host:

curl http://localhost:8080/api/users
porque isso simula o acesso real do usuário.

8️⃣ Resumo simples
Erro que você viu:

curl: Failed to connect to localhost:8080
significa:

container → tentou acessar ele mesmo
mas o servidor está em outro container
9️⃣ Você já chegou num nível importante
Você agora já domina:

Docker multi-container

<?php

namespace App\Controllers;

use App\Models\UserModel;                        // importa o model

// isso é um dock block para poder melhorar as pesquisas
/**
 * @property \CodeIgniter\HTTP\Response $response
 * @property \CodeIgniter\HTTP\IncomingRequest $request
 */


class UserController extends BaseController      // obrigatorio extender
{
    public function index()                      // nome da funçao
    {
        $userModel = new UserModel();            // instancia o model (cria ele na memoria)

        $users = $userModel->findAll();          // vai no banco buscar tudo

        return $this->response->setJSON($users); // retorna o objeto http da resposta para permitir o encadeamneto -> 
    }

    public function store()                      // metodo store armazenar usuario [2026-02-27 10:09]
    {
       $userModel = new UserModel();             // 1. cria uma nova instancia do modelo UserModel

       // 2. Pega o corpo da requisição esperando que venha em formato JSON
       //    O true como parâmetro faz o CodeIgniter converter o JSON em array associativo
       $data = $this->request->getJSON(true);    

       // 3. Verifica se o campo 'name' existe no JSON e se não está vazio
       if (!isset($data['name']) || empty($data['name'])) {
           // 4. Se não veio o nome ou veio vazio → retorna erro 400 (Bad Request)
           return $this->response->setJSON([
               'error' => 'Nome é obrigatório'
           ])->setStatusCode(400);
           // Obs: o return encerra a execução do método imediatamente
       }
       
       // 5. Se chegou aqui é porque tem nome → faz a inserção no banco de dados
       //    O método insert() do modelo geralmente faz INSERT INTO users ...
       $userModel->insert([
           'name' => $data['name']
           // Aqui poderiam vir mais campos, ex: 'email', 'password', etc.
       ]);

       // 6. Retorna resposta de sucesso com status 201 (Created)
       return $this->response->setJSON([
           'message' => 'Usuário criado com sucesso'
       ])->setStatusCode(201);
    }

    // update
    public function update($id = null)      // nome da função
    {
      $userModel = new UserModel();         // instancia cria o model na memoria $userModel

      $user = $userModel->find($id);        // find() busca no banco um unico registro pelo id

      if (!$user) {                         // true or false se não encontrar o $user no banco
          return $this->response->setJSON([        // setJSON() converte array e obj em string json e recebe ler no body e headers
              'error' => 'Usuário não encontrado'  // retorna um erro em formato json como resposta  
          ])->setStatusCode(404);                  // 404 indica que estabeleceu a conexao mais nao encontrou 
      }                                            // o recurso

      $data = $this->request->getJSON(true);       // le dados json enviados no body  true faz o retorno ser um array associativo  
                                                   // resutado final data é um array associativo do json recebido
      $userModel->update($id, [                    // update() atualiza um registro existente ela permite passar um array de dados
          'name' => $data['name'] ?? $user['name'] // true??false se data tiver um nome use ele se nao use(mantenha) o do usuario
      ]);
      
      return $this->response->setJSON([                  // a resposta é em json no body e no headers que o usuario foi atualizado
          'message' => 'Usuário atualizado com sucesso'  // Content-Type: application/json
      ]);

    }

    // delete
    public function delete($id = null)
    {
        $userModel = new UserModel();
    
        $user = $userModel->find($id);
    
        if (!$user) {
            return $this->response->setJSON([
                'error' => 'Usuário não encontrado'
            ])->setStatusCode(404);
        }
    
        $userModel->delete($id);
    
        return $this->response->setJSON([
            'message' => 'Usuário removido com sucesso'
        ]);
    }
}

Ahh, agora entendi o que está acontecendo com você. Isso não é erro seu — é como o CodeIgniter funciona quando você carrega ele dentro do php -a.

Quando você faz:

require 'public/index.php';
o index.php não apenas carrega o framework, ele também executa o ciclo HTTP completo do CodeIgniter. Depois que termina, o script encerra a execução internamente.
Resultado: várias funções do framework ficam em um estado meio “travado” dentro do shell interativo, e por isso chamadas como:

config('App');
service('logger');
acabam não retornando nada no php -a.

✔️ Forma correta de carregar o CodeIgniter no terminal
Em vez de carregar public/index.php, carregue o bootstrap do framework.

Dentro do php -a faça:

require 'app/Config/Paths.php';
$paths = new Config\Paths();
require $paths->systemDirectory . '/bootstrap.php';
Isso inicializa o framework sem rodar o ciclo HTTP.

Agora teste:

$config = config('App');
var_dump($config);
Agora você deve ver algo como:

object(Config\App)#...

Boa! 👏 Você achou exatamente o que estava acontecendo.

O problema não era o Model nem o CI4, era o buffer de saída do PHP dentro do php -a.

O CodeIgniter usa output buffering, então no shell interativo o resultado fica preso no buffer e não aparece no terminal até você liberar.

Sua solução funciona porque você forçou o flush do buffer.

✔️ O que sua solução faz
1️⃣ Limpa todos os buffers
while (ob_get_level() > 0) { 
    ob_end_flush(); 
}
Isso remove qualquer buffer aberto pelo framework.

2️⃣ Força o PHP a imprimir imediatamente
ob_implicit_flush(true);
Agora tudo que usar:

echo
print_r
var_dump
aparece direto no terminal.

3️⃣ Teste
echo "TESTE DE VIDA";
var_dump($userModel->find(3));
resultado:

TESTE DE VIDA
array(2) {
  ["id"] => "3"
  ["name"] => "Pedro Pedro"
}
4️⃣ Debug direto no stderr (ótima técnica)
Você também usou:

file_put_contents('php://stderr', print_r($userModel->find(3), true));
Isso escreve direto no canal de erro, ignorando o buffer.

Docker
